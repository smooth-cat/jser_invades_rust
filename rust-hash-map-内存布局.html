一、HashMap 的本质

std::collections::HashMap 只是一层薄包装：真正的实现是 hashbrown（Google SwissTable 的 Rust 移植）。它的全部状态是栈上 48 字节的控制结构，元素本身存放在一段连续的堆分配里。

// std 源码：library/std/src/collections/hash/map.rs pub struct HashMap<K, V, S = RandomState> { base: hashbrown::HashMap<K, V, S>, } // hashbrown 0.17 src/map.rs：概念上只有两个字段 pub struct HashMap<K, V, S> { hash_builder: S, // RandomState：SipHash 1-3 的两个 u64 种子，16 B table: RawTable<(K, V)>, // 哈希表本体 } // hashbrown 0.17 src/raw.rs：核心控制结构，4 个 usize struct RawTableInner { bucket_mask: usize, // 桶数 - 1（桶数恒为 2 的幂，用 & 代替 %） ctrl: NonNull<u8>, // 指向堆上 ctrl bytes 的首字节 C0 growth_left: usize, // 还能插入多少个元素就触发扩容 items: usize, // 实际元素数，即 len() } // 64 位平台：HashMap 概念大小 = 16 + 32 = 48 bytes

HashMap::new() 不做任何堆分配：ctrl 指向一段静态的 EMPTY 表（16 个 0xFF），第一次 insert 才申请堆内存。字段顺序与 ABI 不是稳定承诺，下图按语义字段讲解。

二、内存总览：一段连续分配

每张表在堆上只有一次 alloc，自低位到高位依次是：桶数据（逆序存放）和 ctrl bytes 区。每个桶的“户口”由同下标的 ctrl byte 管理。

// hashbrown 0.17 src/raw.rs 的内存布局注释（概念化） // // [Padding] [T_n … T_1 T_0] [C_0 C_1 … C_{n-1}] [C_0 … C_15 的复制] // \____ 桶数据，逆序 ____/ \___ ctrl 区 ___/ 尾部镜像 // ^ // ctrl 字段指向这里（C0） // // 桶 T_i 的地址 = data_end - (i + 1) × size_of::<(K, V)>() // data_end == ctrl 指针：桶 0 紧贴在 ctrl 区之前，越靠后的桶地址越低 // // ctrl 区长度 = 桶数 + 16： // · C_0..C_{n-1} 真实 ctrl byte，每个桶一个 // · 小表(<16 桶) 中间夹一段恒为 EMPTY 的填充字节 // · 末尾 16 字节复制开头 16 字节：组加载越过表尾时读到的是“回绕”数据

ctrl byte 的三种状态

// hashbrown 0.17 src/control/tag.rs Tag::EMPTY = 0b1111_1111 // 0xFF 空槽：探测在这里终止 Tag::DELETED = 0b1000_0000 // 0x80 墓碑：探测继续前进（remove 产生） // 其余 0b0hhh_hhhh（0x00..=0x7F）= FULL：64 位 hash 的最高 7 位，记作 h2

一次探测用 SIMD 一口气加载 16 个 ctrl byte，用一条指令筛出“h2 相同”的候选，再逐个比较 key。h2 只有 7 位，可能误报，但把昂贵的 key 比较从 16 次压缩到极少数几次。

三、h1 / h2 / pos 是怎么生成的：每个参数讲清楚

查找和插入共用同一条流水线：key → hash → (h2, pos) → ctrl byte 与桶的物理地址。下面分四步走，每一步用到的每个数字（57、0x7f、bucket_mask、16……）都交代来历。

步骤 ①：key → hash（64 位）

hash 是整条流水线的唯一输入，它由哈希函数生成——把任意长度的 key 压缩成固定 64 位，且分布均匀：

// 标准库：make_hash —— key 的字节流喂给 SipHash 1-3，压缩出一个 u64 let hash = { let mut hasher = hash_builder.build_hasher(); // hash_builder = RandomState（见下） k.hash(&mut hasher); // 把 key 的字节逐个喂进去 hasher.finish() // → 64 位，例如 0x08b74207b55c5cbc }; // RandomState 内部是两个 u64 种子 k0、k1： // · 进程启动时随机生成一次（线程局部，每个 HashMap 实例再叠加一个计数） // · 所以同一份代码每次运行、每个 map 实例，hash 都不同 —— 攻击者无法预测 // 哪些 key 会撞在同一个桶上，这是抗 HashDoS 攻击的防线 // 本页示例换成固定种子的 FNV-1a 64 以便复现： // h 初值 = 0xcbf29ce484222325，对 key 的每个字节：h ^= 字节; h *= 0x100000001b3

对 hash 的唯一要求是位模式足够随机：后面 h2 靠它筛候选、pos 靠它均匀落桶。换成 ahash / fxhash 等更快的函数也行，但会失去 RandomState 的防碰撞保证。

步骤 ②：hash → h2（取最高 7 位做“指纹”）

h2 = (hash >> 57) & 0x7f // │ └─ 0x7f = 0b0111_1111：7 个指纹位的掩码（64 位下右移已只剩 7 位， // │ 此处是双保险；32 位平台移位量变为 25，靠它保证写法一致） // └─ 57 = 64 − 7：右移丢掉低 57 位，把最高 7 位顶到最低位上 // hash("ip") = 0x08b7…5cbc：最高字节 0x08 = 0b0000_1000 → 最高 7 位 = 0000100₂ → h2 = 0x04

为什么恰好 7 位？因为 h2 要存进 1 字节的 ctrl byte，而那个字节的最高位必须留作状态位（见下图）。& 0x7f 在 64 位平台上是双保险（右移后本来就只剩 7 位），32 位平台上移位量变为 25，掩码保证写法一致——hashbrown 源码 Tag::full 正是这么写的。

步骤 ③：hash → pos（取低位 + 掩码）

bucket_mask = buckets - 1 // 4 桶 → 3，8 桶 → 7，16 桶 → 15 pos = h1(hash) & bucket_mask // h1 就是 hash 本身（hash as usize，64 位全保留） // 4 桶表：hash("ip") 的低 2 位 = 0b00 → pos = 0；8 桶表则看低 3 位 = 0b100 → pos = 4 // & mask 与 % buckets 完全等价（桶数是 2 的幂时），但取模是除法指令，& 只需一条 and
bucket_mask 详解：为什么 −1，它到底管什么
buckets = 8 = 0b1_000 // 2 的幂：二进制里只有一位是 1 mask = 7 = 0b0_111 // 减 1 后：这一位塌成低位全 1 —— 1 的个数 = log2(8) = 3 任意 u64 x = 0b…1_0110_1010 pos = x & 0b0_111 = 0b010 // 高位全清零、低 3 位原样保留 → 结果必然 ∈ [0, 7]
1
−1 的原因：2 的幂只有一位是 1，减 1 恰好把它换成“低位全 1”（0b1000 − 1 = 0b0111）。全 1 的位数 = log2(桶数) = 给所有桶编号所需的位数。
2
& 掩码的一箭双雕：既等价于 % 桶数（让 hash 均匀落到每个桶），又是免费的越界保护——结果永远在 0…桶数−1 之内，不需要任何 if 判断。
3
反例说明为什么必须是 2 的幂：若桶数 = 6，mask = 0b101 不再全 1——bit 1 恒被清零，下标 2（0b010）和 3（0b011）永远映射不到，部分桶永远空着。所以容量只能沿 4 → 8 → 16 → 32 翻倍。
4
还有一个数学硬约束：三角探测的“每组恰好访问一次”只在 mod 2ⁿ 下成立（第九节），非 2 的幂会漏探某些组，探测可能永远遇不到 EMPTY。
bucket_mask 的三处出场表达式做的事
定起点pos = h1 & bucket_mask任意 64 位 hash 钳成合法桶下标
管回绕pos = (pos + stride) & bucket_mask探测越过表尾时自动绕回开头
折映射(p + j) & bucket_mask · ((i−16) & bucket_mask) + 16组内第 j 字节 / 镜像下标 → 桶下标

正因为处处要用，RawTableInner 里存的字段干脆就是 bucket_mask 而不是桶数——桶数随用随算：num_buckets() = bucket_mask + 1。它还顺便决定容量：bucket_mask < 8 时容量 = mask 本身（4 桶装 3、8 桶装 7，强制留一个 EMPTY）。

h1、h2 的命名来自 SwissTable 论文：h1 管位置（只看低位），h2 管指纹（只看高位），两者其实是同一个 hash 的不同区段。

查找 get("ip") 的定位链条（满载 4 桶表，基址 0x7f3a_00a0，ctrl = 0x7f3a_0100）

1
现算 hash：把 "ip" 的两个字节 0x69 0x70 喂给哈希函数 → hash = 0x08b74207b55c5cbc。表里没有存 hash，每次调用都重算。
2
一拆为二：h2 = (hash >> 57) & 0x7f —— 最高 7 位 0000100₂ → h2 = 0x04（待比较的指纹值）；pos = hash & 0b11 —— 最低 2 位 0b00 → pos = 0（起始下标，4 桶表 bucket_mask = 3）。
3
读组：Group::load(ctrl + 0) —— 从地址 0x7f3a_0100 一条 movdqu 连读 16 字节，覆盖 0x7f3a_0100…0x7f3a_010f。
4
组内容 = [C₀=0x04, C₁=0x1e, C₂=0xFF, C₃=0x03, C₄…C₁₅=0xFF]：真实 ctrl 4 字节 + 恒 EMPTY 的填充 12 字节（4 桶表的 group@0 还够不到镜像区）。
5
SIMD 筛指纹：一条 pcmpeqb 让 16 字节各自与 0x04 比较 → 16 位掩码 0b…0000_0001，只有 bit 0 命中。逐个核对：C₀ = 0x04 ✓；C₁ = 0x1e ✗；C₃ = 0x03 ✗；C₂、C₄…C₁₅ = 0xFF ✗。
6
换算桶下标：命中位 j = 0 → 下标 = (pos + j) & bucket_mask = (0 + 0) & 3 = 0。
7
换算桶地址：bucket(0) = data_end − (0+1) × 24 = 0x7f3a_0100 − 0x18 = 0x7f3a_00e8（基址 +72）—— 逆序布局中下标 0 离 ctrl 最近。
8
读桶并比较 key：从 0x7f3a_00e8 读出 T₀ = ("ip", 1)，"ip" == "ip" ✓。若 key 不等 → 回组内下一个匹配位；无匹配且组含 EMPTY → None（右侧 get("zz") 走的正是那条路）。
9
返回 Some(&1)。全程：1 次组加载、0 次探测跳跃、1 轮 SIMD 指纹比较、1 次 key 比较。

插入 insert("key") 的定位链条（插入前：ip@0、42@3，items = 2，growth_left = 1）

1
reserve(1)：growth_left = 1 ≥ 1 → 空间足够，不触发 rehash，直接探测。
2
hash("key") = 0x3dc94a19365b10ec → h2 = 0x1e（最高 7 位 0011110₂）、pos = hash & 0b11 = 0b00 = 0。
3
读组：Group::load(0x7f3a_0100) → [0x04, 0xFF, 0xFF, 0x03, 0xFF ×12]（此刻 C₁ 还是 EMPTY——key 尚未写入）。
4
找插入槽：筛 h2 匹配位 → 无一字节等于 0x1e → key 必不存在，一次 key 比较都不用做；同时记下首个 EMPTY/DELETED = byte 1 → 插入下标 (0 + 1) & 3 = 1；组内含 EMPTY → 探测到此终止。
5
写 ctrl byte：地址 0x7f3a_0101（ctrl+1）← 0x1e；同步写镜像：下标 ((1−16) & 3) + 16 = 17 → 地址 0x7f3a_0111 ← 0x1e。
6
写桶数据：bucket(1) = 0x7f3a_0100 − 2 × 24 = 0x7f3a_00d0（基址 +48）→ T₁ ← ("key", 3)。
7
记账：growth_left 1 → 0（EMPTY→FULL 各扣 1），items 2 → 3 —— 表已满载，下一次 insert 将进入第七节的扩容流程。

下标换算一览：探测组 p 内第 j 字节 → 下标 (p+j) & mask；下标 i 的 ctrl byte → ctrl+i；下标 i 的桶 → data_end−(i+1)×stride；镜像 → ((i−16)&mask)+16。整张表只有 ctrl 一个指针，data_end 就是它——桶的“下标 0”离 ctrl 最近，越靠后的桶地址越低。

get("zz") → None：假阳性 + 镜像回绕

1

3

探测只被 EMPTY 终止，DELETED 墓碑不会——这是墓碑存在的全部意义。h2 只有 7 位，假阳性在所难免，最终由完整的 key 相等性兜底。

常见误区：pos 不是指纹。pos 是下标——回答“去哪找”（hash 低 log2(桶数) 位）；h2 是字节值——回答“命中后比什么”（hash 高 7 位）。无碰撞时 get("ip") 的核心判定恰好可写成 ctrl[pos] == h2：下标 0 处的字节值是 0x04。即便某个 key 的 h2 数值恰好等于它的 pos，也只是巧合——两段位互不参与对方的运算（见第三节）。

那 ctrl[pos] 是不是就是它的指纹？只要插入时组内首个空位恰好是起始位，就是——ip 作为第一个元素插在起始位 0，ctrl[0] = 0x04，get 第一步比较就命中。反例是 "key"：pos 同样为 0，但桶 0 已被占，它落到组内首个空位桶 1，指纹 0x1e 存在 ctrl[1] 而非 ctrl[0]，get 靠组内逐位匹配（bit 1）找到它。更本质地说：表里没有任何地方记录“key 在哪”，get 之所以总能找到，是因为探测路径是确定性的——同一 hash + 同一 ctrl 布局，必然重放插入时的路径（remove 只改标记不搬元素；resize 会让布局重洗，但重放依然成立）。

五、insert：reserve → 探测 → 写入

第一步 reserve(1)
growth_left < 1 ? 先 rehash : 直接探测

空间不足时先扩容或原地 rehash（见第七节）。即使 key 已存在也可能先触发——这是 HashMap::insert 的实现顺序。

第二步 逐组探测
pos = h1 & bucket_mask

每组筛 h2 匹配位并比较 key（找到 → 原地覆盖 value，返回 Some(旧值)）；同时记下组内首个 EMPTY 或 DELETED 的槽位。

第三步 终止条件
group 含 EMPTY → 停

停在第一个含 EMPTY 的组，用记下的槽位插入——保证不会越过“本可插入的空位”继续找。

第四步 写入内存
ctrl[i] = h2 · T_i = (K, V)

写 ctrl byte（含镜像）；槽位原为 EMPTY 则 growth_left -= 1，原为 DELETED 则不变；items += 1。

七、扩容：growth_left 耗尽时

每个 HashMap::insert 都先 reserve(1)。当 items 达到容量上限（桶数 × 7/8，小表另计）时 growth_left 归零，下一次插入触发 rehash：

// hashbrown 0.17 src/raw.rs fn bucket_mask_to_capacity(bucket_mask: usize) -> usize { if bucket_mask < 8 { bucket_mask } // 4桶→3, 8桶→7：至少留 1 个 EMPTY else { ((bucket_mask + 1) / 8) * 7 } // 16→14, 32→28, 64→56 … } fn capacity_to_buckets(cap: usize) -> usize { if cap < 15 { /* 小表阶梯：<4 → 4 桶，<8 → 8 桶，否则 16 桶 */ } (cap * 8 / 7).next_power_of_two() // 大表按 7/8 取整到 2 的幂 }
capacity_to_buckets 完整逻辑：想装 cap 个元素 → 开多少桶（raw.rs ~L103-163）
输入 cap：想容纳的元素数（≥ 1；cap = 0 不会进来 —— HashMap::new 根本不分配） · table_layout.size：(K, V) 的字节数
①
分支边界 cap < 15：小表用写死的阶梯，大表用公式。边界选 15 让两条路无缝衔接：14×8/7 = 16 还在“16 桶”世界（阶梯的第三档），15×8/7 = 17 → 取 2 的幂 = 32 —— 阶梯管 4/8/16 桶，公式管 ≥ 32 桶，不多不少。
②
小表分支 · min_cap 档位：按 (Group::WIDTH, (K,V) 字节数) 选档——≤1B → 14；2..=3B → 7；其余 → 3。目的是保证 桶数 × 元素大小 ≥ ctrl_align(16)：源码注释的表格（size = 1 字节）显示 4 桶分配 36B ÷ 3 元素 = 12 B/元素 (Yikes!)，16 桶才降到 3.4 —— 元素太小就抬高容量摊薄 ctrl 区开销。
③
小表分支 · 抬升 + 阶梯：cap = max(min_cap, 请求)，然后写死三档：<4 → 4 桶；<8 → 8 桶；否则 16 桶。没有 2 桶——容量只有 1，插满即扩（源码注释原话）；没有 1 桶——mask = 0 是“未分配单例”的哨兵。4 桶容量 3，强制留 1 个 EMPTY 保探测终止。
④
大表分支（cap ≥ 15）：cap × 8 / 7（7/8 负载的倒数——要装 cap 个至少要这么多槽，整数除法截断）→ next_power_of_two() 向上取 2 的幂。例：15 → 17 → 32 桶；100 → 114 → 128 桶。checked_mul 溢出返回 None → 就是那个著名的 capacity overflow panic 的出处。
⑤
兜底断言：ensure_bucket_bytes_at_least_ctrl_align 校验 桶数 × size ≥ 16（debug 断言，release 空操作）。大表分支最小 32 桶，size = 1 也有 32 字节，天然满足。

首次 insert 为什么恰好开 4 个桶？—— 三个常量的合谋（raw.rs capacity_to_buckets，~L104）
fn capacity_to_buckets(cap: usize, table_layout: TableLayout) -> Option<usize> { if cap < 15 { let min_cap = match (Group::WIDTH, table_layout.size) { (16, 0..=1) => 14, // (K, V) ≤ 1 字节 (16, 2..=3) | (8, 0..=1) => 7, // (K, V) ≤ 3 字节 _ => 3, // 典型大小（(&str, i32) = 24 字节落这里） }; let cap = min_cap.max(cap); // We don't bother with a table size of 2 buckets since that can only // hold a single element. Instead, we skip directly to a 4 bucket table // which can hold 3 elements. let buckets = if cap < 4 { 4 } else if cap < 8 { 8 } else { 16 }; return Some(buckets); } (cap * 8 / 7).next_power_of_two() // cap ≥ 15 的大表分支 }
1
请求从 1 开始：首次 reserve(1) 走 reserve_rehash_inner（~L2739）：单例表容量 0 → resize 目标 = max(0 + 1, 0 + 1) = 1（~L2786）——只请求“再放 1 个”。
2
常量一 min_cap = 3：按 (Group::WIDTH, (K,V) 大小) 分档，典型大小 ≥ 4 字节落 _ => 3 → cap = max(3, 1) = 3。2 桶被跳过的理由写在源码注释里：2 桶只能装 1 个元素，插一个就满、下次立刻扩——索性直接开 4 桶装 3 个。
3
常量二：阶梯里的字面量 4（~L141）：`cap = 3 < 4` → buckets = 4。这就是“4 桶起步”的直接出处——不是算出来的，是阶梯的最低档写死的。
4
特例：极小 (K, V) 首次开得更大——size 2..=3 字节 → 8 桶；size ≤ 1 字节 → 16 桶。原因：桶数据总字节必须 ≥ ctrl 对齐（16），元素太小就多要几个摊薄 ctrl 区的开销（ensure_bucket_bytes_at_least_ctrl_align）。非 SSE2 平台（WIDTH = 8）只有 size ≤ 1 字节才拿 14 → 16 桶。

所以“4 桶起步”只对典型 K / V 成立：本页的 HashMap<&str, i32> 首次开 4 桶、装 3 个（growth_left = 3），第 4 次 insert 才扩到 8——正是下方演示；而 HashMap<u8, ()>（(K, V) 共 1 字节）首次 insert 直接开 16 桶。

"ip"0b10004+4：落在自己的新 pos 上（新增位 bit2 = 1 → 旧下标 + 旧桶数）
"key"0b10015+4：新 pos 与 ip 相同（都是 4），搬运按旧桶序、ip 先到 → 顺延一格；与 ip 的相对距离保持

1
裂桶规律：mask 从 0b11 换成 0b111 = 多看一位。旧桶 i 的元素只可能去新桶 i（新增位 = 0）或 i + 4（新增位 = 1）——4 桶表裂成 0/4、1/5、2/6、3/7 四对，绝不会跑去别的桶。
2
同组相对次序保持：ip 与 key 的新 pos 相同（低 3 位都是 0b100），搬运按旧桶下标升序（源码 FullBucketsIndices），ip（旧桶 0）先落 4，key（旧桶 1）顺延到 5 —— 旧表里 key 本就跟着 ip 一格，新表依旧。
3
C 与 T 成对搬、指纹不变：hash 重算结果与插入时相同，h2（0x04 / 0x1e / 0x03）原样写进新下标并双写新镜像；T 是 ptr::copy_nonoverlapping 按字节的位拷贝，随后旧分配整块释放——元素不会被 drop 两次。
4
墓碑就地蒸发：遍历器只挑 FULL 桶，DELETED 根本不参与搬家——这就是“扩容顺带清理墓碑”。growth_left 与 items 在全部搬完后统一记账（新容量 − items）。

“key 重新哈希”的准确含义：hash 结果不变（种子在 map 存活期内固定），重新执行的是“算 hash + 重新探测”这两步——因为表里不缓存 hash。变的是取位位数（低 2 位 → 低 3 位）与探测布局。若旧表里 key 先于 ip 插入，这里 key 会占 4、ip 顺延到 5：布局不同但同样合法。

// 扩容时每个元素都要重新 hash + 重新定位吗？—— 是，无一例外（raw.rs resize_inner） for full_byte_index in self.full_buckets_indices() { let hash = hasher(self, full_byte_index); // ~L2906：重算 hash，一个都不少 let (new_index, _) = new_table.prepare_insert_index(hash); // ~L2918：重新定位 // └ find_insert_index：pos = h1 & 新mask → 组内首个空位 // └ fix_insert_index：小表伪命中修正（4 桶 < Group::WIDTH 16，每次落位都过这道检查） // copy_nonoverlapping 搬 (K, V) —— 唯一省掉的是 key 比较（元素已知唯一、新表无墓碑） } // hasher 闭包（~L965，原地 rehash 分支 ~L1013 同款）： // |table, index| hasher(table.bucket::<T>(index).as_ref())

为什么不能跳过？桶里只有 (K, V)、ctrl 里只有 7 位指纹——表里没存 hash，想知道 key 该去哪只能重调 hasher。三个易错点：① 重算结果与当初完全相同（种子固定，布局是确定性的）；② "42" 这类没动的元素也照样重算——重算是为了“知道该去哪”，新位置恰好等于旧位置只是结果；③ 代价 = O(n) 次 hash + O(n) 次探测定位 + O(n) 次拷贝，这正是 resize 是 O(n)、insert 只是均摊 O(1) 的来源。对比：Java HashMap 的 Node 里缓存了 int hash（扩容可免 hasher 调用，但重新定位仍不可避免——布局变了；代价是每元素多 4-8 字节）——Rust std 选择省内存，把成本留到 resize。

九、哈希与探测的数学

// 一个 64 位 hash 被拆成两部分使用 h2(hash) = (hash >> 57) & 0x7f // 高 7 位 → ctrl byte，供 SIMD 快速筛候选 h1(hash) = hash as usize // 低位 → 决定桶位置 // 探测序列：三角数探测（triangular probing），以“组”为单位跳跃 pos_0 = h1(hash) & bucket_mask // 起始组 stride += 16; pos_k = (pos + stride) & bucket_mask // 组偏移依次为 0, 16, 48, 96, 160, …（16 × 1, 3, 6, 10, 15 三角数） // 数学保证：mod 2^n 时每个组恰好被访问一次，必在遇到 EMPTY 前覆盖全表 // 标准库的 hash：SipHash 1-3，种子来自 RandomState（每进程随机，抗 HashDoS） let mut map = HashMap::new(); // 相同的 key 每次运行得到不同 hash // 追求极致性能可换 fxhash / ahash 等，但需自担碰撞风险
为什么用“组 + ctrl bytes”而不是逐槽比较
1
一次 movdqu 加载 16 字节，一条 pcmpeqb 同时比较 16 个 h2 —— 把 16 次内存访问压成 1 次。
2
负载因子 7/8 保证 16 字节的组平均只有 14 个 FULL，h2 匹配平均约 0.1 个，昂贵的 key 比较近乎消失。
3
尾部镜像让任意位置的 group 加载都能安全读满 16 字节，无需分支处理表尾回绕。
为什么是三角探测，而不是相邻组逐个（线性）探测？
// 三角序列长这样（hashbrown 0.17 src/raw.rs ProbeSeq::move_next，就两行） stride += 16; pos += stride; pos &= bucket_mask; // 组偏移：0, 16, 48, 96, 160, … = 16 × (0, 1, 3, 6, 10, …) —— 每步多跳一组
1
淘汰“相邻组线性”（stride 恒 16）——数学上可行，性能上出局：它的窗口恰好不重叠地铺满一圈，每个组都会被访问（覆盖性没问题）。致命伤是聚集：home 相差 16 倍数的 key（32 桶表里概率 1/16）探测序列完全锁步——A 走 0,16,32,48，B 走 16,32,48,0，从第二步起 Bk ≡ Ak+1，碰撞链必然并轨越滚越长；爬过长度 L 的连续满组要 L 步。
2
淘汰“普通二次探测 k²”——正确性直接出局：桶数是 2 的幂，而 k² mod 8 只可能取 {0, 1, 4} —— 8 个组只访问 3 个，剩下 5 个组永远探不到：装在那里的元素永远找不到，探测也永远遇不到含 EMPTY 的组（死循环）。在“桶数 = 2 的幂”的世界里，随手写一个二次式几乎必漏。
3
三角数的置换定理（入选资格）：组数 G = 2m 时，前 G 个组偏移 Tk = k(k+1)/2 mod G 恰好是 0…G−1 的完美置换——G=8 实测：0,1,3,6,2,7,5,4 ✓。证明一行版：若 Ti ≡ Tj (mod 2m)，则 (j−i)(j+i+1) ≡ 0 (mod 2m+1)；但 j−i 与 j+i+1 一奇一偶（和为 2j+1），偶因子的 2 幂 ≤ m，矛盾。这正是源码注释引用的 fgiesen 博文（triangular-numbers-mod-2n）的结论——于是 G 步内每组恰被访问一次，配合负载因子保证必然撞上含 EMPTY 的窗口，探测必然终止。
4
跳聚集区的红利：第一跳 +16 相当于继续线性扫描；随后每步多跳一组——k 步覆盖 k(k+1)/2 个组，越过长度 L 的连续满聚集区只要 O(√L) 步，而线性要 O(L) 步。两条序列即使相遇，下一步的跳距已不同，落点随即分散（64 桶表实测：home 0 与 home 16 的三角序列每一步都落在不同窗口：0,16,48,32 对 16,32,0,48；线性则是逐位锁步）。
5
小表根本不用出场：桶数 < 16 时组数 = 1，第一步的窗口经镜像覆盖全表，容量又强制留 EMPTY——一步必停。
