Rust 内存安全：ptr::read 与悬垂指针的误读现场

指针逃逸调用帧 → 栈帧内存被下一个调用复用 → 按位拷贝读出“别人的数据”。对应源码 src/ob_01_unsafe.rs，右侧动画支持单步 / 自动播放，逐步观察每个关键执行点的内存布局。

结构体大小
Person = 24 字节
只有 name: String：栈上 (ptr, cap, len) 各 8 字节，内容在堆上。
关键动作
ptr::read::<Person>(p)
把 p 指向的 24 字节按位拷贝一份：不查借用、不查有效性、不清空原数据。
问题的起点
return a_ptr
返回指向 a 调用帧的指针。栈帧弹出后，地址值还在，内存已不属于任何人。
栈内指针 堆内指针 合法持有 按位拷贝 / 可疑 悬垂指针（红虚线） 已释放内存（虚线框）

回看：为什么编译器一个警告都不给？



  unsafe 只关闭了警报，没有把未定义行为变成合法行为。
  裸指针 *const T 不携带生命周期信息，类型系统无法知道 0x7ff198 背后的栈帧已经消亡；
  ptr::read 的契约是“由调用者保证有效性”，于是责任从编译器转移到了程序员头上。
  本例同时踩了三条线：读悬垂指针、凭空制造第二份 Person 导致堆资源双重持有、mem::forget 打破 RAII 析构链。




  图中的“b 复用 a 的栈地址”是最典型的情形，但不是保证。
  真实运行中 b 的帧是否恰好落在同一片地址取决于编译器布局与调用约定；而且 UB 允许编译器假设“它不会发生”，release 构建甚至可能把整段读取优化掉。
  用 Miri 直接验证：cargo +nightly miri ob_01_unsafe（或跑对应测试）会立即报出 Undefined Behavior，指出对已消亡栈帧内地址的读取。
